# TODO

The working plan for this fork of Gemini Desktop: what to do next, in what order, and what is already done.
This file is how progress is remembered between sessions, for people and AI agents alike.
The evidence behind each item is in [docs/CODEBASE_OVERVIEW.md](docs/CODEBASE_OVERVIEW.md); bug IDs such as B1 point there.

## How to use this file

- Read it before starting work. Unless asked for something else, take the first open item in the current focus.
- Every item has an ID. Use it in the branch name, the commit message and the PR title, for example `L2: add pacman target`.
- In the PR that does the work, tick the item, link the PR, and add a line to the [Done log](#done-log). Mark work in flight as `[~]` with its PR link.
- New problems become new items in the right section, not notes in a chat.
- Items marked **(owner)** need Jared: an account, a secret, a repository setting, or a test on real hardware.
- Keep every feature and keep Windows building. An item that would drop a feature needs the owner's OK first.

Legend: `[ ]` open, `[~]` in progress, `[x]` done, `[!]` blocked (say on what).

List the seven dependencies whose scripts run today (Electron's binary download, esbuild, node-llama-cpp, the `usocket` build, two WDIO driver downloads and electron-winstaller) by name, so version updates keep working. - [x] **L18** Sign-in from Gemini's own Sign in button (B14) showed Google's "401. That's an error. The server cannot process the request because it is malformed." The button navigates the tab's iframe to `accounts.google.com`, and Google refuses its sign-in pages inside an iframe: the same request gets the 401 only with `Sec-Fetch-Dest: iframe`, with Electron's user agent and with Chrome's. The main window now opens a tab's navigation to a Google accounts page in the sign-in window and reloads after that window closes. The CachyOS test still showed the 401: a server redirect can also send a loading tab there, which the first fix missed (reproduced with the live check, T5). - [x] **L19** Building the deb, rpm and pacman packages on an Arch-based host needs `libxcrypt-compat`: electron-builder's bundled fpm runs on a Ruby that loads `libcrypt.so.1`, and Arch only ships `libcrypt.so.2`. CI builds on Ubuntu and installed packages are unaffected. Documented in `AGENTS.md` and the overview's build recipe, [#2](https://github.com/ClickCalickClick/gemini-desktop/pull/2).
- [x] **L20** Quitting at logout crashed the app (B15). A logout, a shutdown or `pkill gemini-desktop` sends SIGTERM to all of the app's processes. The zygotes die too, so Chromium cannot start a new GPU process, and it ends the app with "GPU process isn't usable. Goodbye." (SIGTRAP and a crash report; on CachyOS the app then hung until SIGKILL). The app's own SIGTERM and SIGINT listeners never ran, because Electron replaces them while starting, and its crash handlers reloaded windows whose renderer had exited, the main window twice. On Linux, `src/main/utils/terminationSignals.ts` now takes SIGTERM, SIGINT and SIGHUP over once the app is ready: when the app's other processes are dying too, the app ends at once by the same signal; otherwise it quits normally, which saves cookies. Windows are not reloaded while quitting or after a clean exit, and at most three times a minute (`rendererReloads.ts`). The live check's `--stop-all` tests it: in a container the old app crashed in 3 of 4 tries and the new one quit cleanly in all 17. On CachyOS on 2026-10-14 it ended at once by SIGTERM in 3 of 3 runs with `--stop-all`, and quit with exit code 0 after a SIGTERM to its main process alone. `coredumpctl` there lists a core dump at the time of each earlier hang, so the app most likely hung while its crash was being saved, [#2](https://github.com/ClickCalickClick/gemini-desktop/pull/2).
- [x] **L21** Sending a Quick Chat left the main window behind other apps on GNOME Wayland (B16): the question reached Gemini, but the window did not come forward. On Wayland an app asks the desktop to raise its window with an activation token, and GNOME refuses that request for a window that is already open, so the window only says it is ready. GNOME does put a newly shown window in front with the focus, which is why Peek and Hide works. `PlatformAdapter.bringToFront()` now hides and shows the main window again on Wayland when it is open but not focused, and every path that brings the main window forward (Quick Chat, Voice Chat, the tray toggle) uses it through `WindowManager.focusMainWindow()`; the other platforms keep `show()` and `focus()`. Reproduced and fixed on a headless mutter 46 in a container with real key presses from mutter's remote desktop API: before the fix another app kept the focus after Enter, after it the main window had the focus within 300 ms. [#2](https://github.com/ClickCalickClick/gemini-desktop/pull/2)

## Phase H: Hybrid Quick Chat, agent features and desktop looks

Quick Chat decides per prompt whether a Gemini web tab or the local agent CLI answers it. The web tab keeps everything only gemini.google.com has (Gems, Canvas, Deep Research, images, Live, history on the phone); the agent adds what a web page cannot do: local files, commands, structured answers. Never use `--dangerously-skip-permissions`; anything that changes files goes through a plan the user confirms in Quick Chat.

[#3](https://github.com/ClickCalickClick/gemini-desktop/pull/3)
